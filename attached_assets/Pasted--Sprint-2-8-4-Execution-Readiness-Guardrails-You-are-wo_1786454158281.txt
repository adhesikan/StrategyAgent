# 2. Core concept

Create a deterministic execution-readiness result for a proposed options order.

The system should answer:

**Can this order safely proceed to user review/confirmation?**

Possible states:

* `READY`
* `READY_WITH_WARNINGS`
* `BLOCKED`

Do not use vague labels such as PASS/FAIL without context.

Each result must include structured findings.

Example:

```ts
type ExecutionReadinessStatus =
  | "READY"
  | "READY_WITH_WARNINGS"
  | "BLOCKED";

type ExecutionReadinessFindingSeverity =
  | "INFO"
  | "WARNING"
  | "BLOCKER";

type ExecutionReadinessFinding = {
  code: string;
  severity: ExecutionReadinessFindingSeverity;
  title: string;
  message: string;
  source?: string;
  legId?: string;
};

type ExecutionReadinessResult = {
  status: ExecutionReadinessStatus;
  findings: ExecutionReadinessFinding[];
  evaluatedAt: string;
};
```

Reuse existing types if equivalent structures already exist.

# 3. Readiness categories

Evaluate the order across these categories:

## A. Market Data Readiness

Check:

* quote availability
* quote freshness
* bid/ask availability
* option leg quote availability
* aggregate quote freshness
* wide spreads
* zero bid where relevant
* crossed/invalid markets
* market open/closed state if available

Hard blockers:

* required quote unavailable
* stale quote beyond configured threshold
* invalid option market
* underlying quote unavailable when required

Warnings:

* unusually wide spread
* low/no bid
* after-hours / market closed where order cannot immediately execute
* partial Greeks only

Reuse the Sprint 2.8.3 quote freshness logic.

Do not duplicate quote classification rules.

---

# 4. Account Readiness

Check whether a broker/account is available.

Potential checks:

* brokerage account connected
* account ID valid
* account status available
* options trading capability
* multi-leg capability
* required options level if broker supplies it
* account restrictions
* account type constraints where known

Do not fabricate unsupported broker capability information.

If the connected broker does not expose a capability:

return a structured warning or `UNKNOWN`, not a fake approval.

Examples:

`BROKER_NOT_CONNECTED` → BLOCKER

`OPTIONS_PERMISSION_UNCONFIRMED` → WARNING or BLOCKER depending on whether submission can legally proceed without confirmation.

`MULTILEG_NOT_SUPPORTED` → BLOCKER

# 5. Position Readiness

Validate holdings/exposure required by the trade.

Examples:

## Covered Call

Verify sufficient shares exist.

Example:

1 short call contract requires 100 shares.

If quantity = 3:

required shares = 300.

If available shares < required shares:

BLOCK.

Finding:

`INSUFFICIENT_COVERED_SHARES`

## Protective Put

Verify underlying shares exist if the trade plan represents protection of an existing position.

If the user is merely buying a standalone put, do not require shares.

Use existing strategy intent/family metadata to differentiate.

## Closing transactions

For close intents:

verify sufficient existing contract quantity where position data is available.

Examples:

`INSUFFICIENT_OPTION_POSITION`

`POSITION_NOT_FOUND`

Do not assume holdings if position data is unavailable.

---

# 6. Buying Power / Capital Readiness

Create a deterministic estimate when possible.

For defined-risk strategies calculate maximum capital requirement from the proposed order.

Examples:

Long call:
premium × 100 × quantity

Long put:
premium × 100 × quantity

Debit spread:
net debit × 100 × quantity

Credit spread:
(max spread width - net credit) × 100 × quantity

Iron condor:
maximum wing risk adjusted for net credit × 100 × quantity

Covered call:
do not treat underlying shares as new capital if shares already exist.

Cash-secured put:
strike × 100 × quantity minus applicable credit, depending on existing project conventions.

For undefined-risk strategies:

do not pretend the application can accurately calculate broker margin.

Return:

`BROKER_MARGIN_CALCULATION_REQUIRED`

and treat as warning/blocker according to execution capability.

If broker provides official buying-power impact, prefer that over local estimates.

Expose both where available:

* estimated capital requirement
* broker-reported buying power impact

Clearly label estimates.

Never call an estimate a broker approval.

# 7. Strategy / Leg Consistency Validation

Validate:

* expected number of legs
* leg directions
* long vs short intent
* same underlying
* expiration relationships
* strike ordering
* quantities
* call/put structure
* defined-risk width
* net debit/credit consistency
* zero or negative invalid quantities

Examples:

Bull call spread:
long lower strike call
short higher strike call

Bear put spread:
long higher strike put
short lower strike put

Iron condor:
correct four-leg ordering

Butterfly:
correct strike relationships

Calendar:
same strike where required
different expiration dates

Do not duplicate the entire strategy builder.

Reuse existing family definitions or strategy metadata where available.

# 10. Liquidity Guardrails

Use available option quote data.

Calculate:

spread dollars

spread percentage relative to midpoint

Example:

```ts
spreadPct = (ask - bid) / midpoint
```

Handle zero/negative midpoint safely.

Possible configurable thresholds:

* warning at > 10%
* severe warning at > 20%

Do not block solely based on wide spread unless an existing VCP execution rule explicitly requires it.

If volume/open interest are available:

support warnings for extremely low liquidity.

Do not require fields the data provider does not supply.

* order pricing direction matches strategy economics

Net debit strategy cannot result in an obviously invalid negative debit due to leg/order construction error.

Use the existing Sprint 2.8.3 pricing computation.

Do not create a second pricing engine.
