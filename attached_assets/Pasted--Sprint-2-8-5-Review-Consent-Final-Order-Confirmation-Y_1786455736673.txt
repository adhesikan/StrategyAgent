# 3. Core concept

The user must confirm a **specific immutable order snapshot**.

The confirmation must answer:

> “Did this authenticated user explicitly review and confirm this exact proposed order, with this exact pricing snapshot, readiness state, and risk context?”

The confirmation must NOT be a generic:

“User clicked confirm.”

It must bind to the exact final review snapshot.

# 4. Final Order Review Snapshot

Create canonical types, preferably in:

`shared/order-confirmation-types.ts`

or extend an appropriate existing shared file.

Suggested model:

```ts
type FinalOrderReviewSnapshot = {
  id: string;
  tradePlanId: string;
  orderPreviewId: string;
  executionReadinessId: string;

  userId: string;

  strategyFamily: string;
  symbol: string;

  legs: FinalOrderReviewLeg[];
```

Reuse existing types wherever possible.

Do not create duplicate leg/pricing representations unnecessarily.

# 5. Snapshot eligibility

A final review snapshot may only be created if:

* execution readiness exists
* execution readiness status is not `BLOCKED`
* required preview exists
* preview has not been superseded
* quote freshness is still acceptable
* user owns/has access to the trade plan
* required server-side broker/account context was used

If readiness is `BLOCKED`:

do not create a confirmation snapshot.

Return a deterministic error.

Suggested code:

`FR_CONFIRMATION_NOT_ALLOWED_BLOCKED`

or use existing naming conventions.

---

# 6. Snapshot immutability

Once created, a final review snapshot must be treated as immutable.

Do not mutate:

* legs
* quantity
* pricing
* account context
* readiness result
* capital estimate
* risk metrics

If underlying order inputs change:

create a NEW snapshot.

Never update the old confirmed snapshot in place.

This is critical for auditability.

---

# 7. Canonical hashing

Create a deterministic canonical representation of the snapshot and compute:

`snapshotHash`

Use a stable cryptographic hash such as SHA-256.

Do not include volatile fields such as:

* createdAt
* expiresAt
* random IDs

inside the hashed business payload unless there is a clear reason.

The hash should bind the business-relevant order state.

Example canonical payload:

```ts
{
  tradePlanId,
  orderPreviewId,
  executionReadinessId,
  userId,
  strategyFamily,
  symbol,
  legs,
  quantity,
  pricing,
  economics,
  readiness,
  marketDataObservedAt,
  reviewedDataVersion
}
```

Sort object keys deterministically.

Ensure repeated creation from identical business state yields the same business hash.

Add tests for determinism.

---

# 8. Snapshot invalidation

A confirmation snapshot becomes invalid if:

* it expires
* the order preview changes
* quantity changes
* legs change
* strikes change
* expirations change
* pricing changes beyond permitted tolerance
* execution readiness changes
* readiness becomes `BLOCKED`
* account changes
* broker changes
* market data becomes stale beyond policy
* trade plan is cancelled/invalidated
* user changes relevant order inputs

Do not silently carry confirmation forward.

Require a fresh review snapshot.

# 9. Confirmation expiration

Create configurable expiry.

Example:

```ts
FINAL_REVIEW_CONFIG = {
  snapshotTtlSeconds: 120,

```

Do not hard-code magic numbers.

If expired:

`EXPIRED`

Require fresh review.

This is especially important for options where quotes move quickly.

# 12. Acknowledgements

Use targeted acknowledgements rather than a giant legal checkbox wall.

Possible acknowledgements depend on the order.

Examples:

## All options orders

* I reviewed the order details.
* I understand options involve risk and may lose value.

## Short options

* I understand short options may be assigned before expiration.

## Defined-risk spread

* I understand the displayed max loss is an estimate based on the entered order terms and may differ because of execution, fees, assignment, or early exercise.

## 0DTE

* I understand this option expires today and can change rapidly.

## Undefined-risk

If future workflow ever supports this:

* I understand potential loss may be substantial or theoretically unlimited.

But Sprint 2.8.4 readiness rules may already block or warn such structures.

Generate acknowledgement requirements deterministically based on findings/order structure.

Do not let the LLM decide which acknowledgements apply.

---

# 13. Required vs informational acknowledgements

Each acknowledgement should contain:

```ts
{
  code: string;
  required: boolean;
  title: string;
  text: string;
}
```

Examples:

* `ACK_OPTIONS_RISK`
* `ACK_SHORT_ASSIGNMENT`
* `ACK_ZERO_DTE`
* `ACK_DEFINED_RISK_ESTIMATE`
* `ACK_MARKET_CLOSED`
* `ACK_BUYING_POWER_ESTIMATE`

Use stable codes.

# 14. Prevent fake consent

The server must verify:

* authenticated user identity
* snapshot belongs to user/trade plan
* required acknowledgement codes were supplied
* all required acknowledgements are present
* snapshot is unexpired
* snapshot is not invalidated
* hash matches current stored snapshot
* current readiness is still acceptable

Do not trust client-side booleans alone.

Client sends acknowledgement codes.

Server validates them.

---

# 15. Server-side revalidation at confirm time

Immediately before accepting confirmation:

revalidate:

* snapshot exists
* snapshot not expired
* snapshot hash valid
* execution readiness not `BLOCKED`
* relevant quote freshness still acceptable
* trade plan unchanged
* preview unchanged
* broker/account identity unchanged where applicable

If anything changed:

return:

`CONFIRMATION_REVIEW_REQUIRED`

Do not silently regenerate and confirm.

User must see the new state.

# 16. Pricing movement tolerance

Do not implement complicated slippage tolerances unless equivalent logic already exists.

A future sprint may add user-defined limit flexibility.
