# 7. Separate Two Different Conditions

A. Current ranking exists, WMT absent

and

B. Current ranking is unavailable/null

into the same user message:

"not a current research candidate"

This is incorrect operationally.

Create canonical distinctions:

`NOT_IN_CURRENT_SNAPSHOT`

`OPPORTUNITY_RANKING_UNAVAILABLE`

`OPPORTUNITY_ENGINE_NOT_INITIALIZED`

`OPPORTUNITY_DATA_DEGRADED`

If ranking is unavailable:

# 8. Make Canonical Opportunity Lookup Self-Healing

This is the preferred architectural improvement.

The persisted PostgreSQL snapshot is the canonical durable source.

Process-local ranking should be an optimization, NOT a single point of truth.

Refactor safely so:

`getCanonicalOpportunity(symbol)`

or the lower-level canonical current-ranking getter can recover if:

`latestRanking == null`

or ranking snapshot identity is stale/missing.

Preferred conceptual flow:

1. Check current in-memory ranking.
2. If valid/current → use it.
3. If missing/uninitialized → load latest persisted snapshot.
4. Compute ranking deterministically.
5. setLatestRanking().
6. retry canonical symbol lookup.
7. Return result.

This should happen through ONE canonical helper, not independently in Trade Planning.

Do not create DB query duplication across every route.

---

# 9. Avoid Request-Level Stampede

If several requests hit an unhydrated instance simultaneously:

only one hydration should occur.

Use:

* shared hydration promise
* mutex
* existing concurrency primitive

Do not let 50 requests all recompute the ranking from DB.

Example conceptual state:

`rankingHydrationPromise`

Requests await the same promise.
