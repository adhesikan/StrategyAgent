Sprint 1.1 — Persist Background Opportunity Snapshots in PostgreSQL

PRIMARY REPOSITORY

Implement this in the existing VCP Trader AI / StrategyAgent repository using Replit.

CURRENT IMPLEMENTATION

The application already has:

- server/services/opportunity-engine.ts
- a non-blocking background scan at startup
- scheduled refresh every four hours
- an in-memory OpportunitySnapshot
- GET /api/opportunities/latest
- dashboard-side independent fetching of the latest snapshot
- no synchronous dashboard MCP scan
- 2,167 passing tests

The current weakness is that the latest snapshot exists only in process memory.

A Railway deployment, restart, crash, or process replacement removes the snapshot and forces users to wait for the next scan.

GOAL

Persist validated Opportunity Engine snapshots in the existing VCP Trader PostgreSQL database.

The engine should:

1. load the latest valid snapshot from PostgreSQL during startup
2. serve that persisted snapshot immediately
3. run the background refresh asynchronously
4. persist successful, partial-success, and valid empty results
5. preserve the last valid snapshot when a refresh fails
6. continue using memory as a fast runtime cache

This is a completion task for Sprint 1.

Do not begin:

- Opportunity Lifecycle
- comparison/change detection
- Watchlist Intelligence
- Research Workspace expansion
- Portfolio expansion
- newsletter work
- persistent MCP market-history caching
- new MCP tools

Do not modify MCP ranking, qualification, scoring, risk, options, portfolio, or execution logic.

Do not commit, push, or deploy automatically.

==================================================
7. CLASSIFY SCAN OUTCOMES
==================================================

Use these definitions:

SUCCESS

A valid result contains one or more qualified candidates.

PARTIAL_SUCCESS

A valid result was returned, but some candidates were unavailable or warnings were present.

EMPTY_SUCCESS

A valid deterministic result was returned with zero qualified and zero watch candidates.

This is not an error.

FAILED

The MCP call failed, timed out, returned an invalid schema, or could not be safely persisted.

Rules:

- SUCCESS, PARTIAL_SUCCESS, and EMPTY_SUCCESS may become the latest valid snapshot.
- FAILED must never replace the latest valid snapshot.
- FAILED may be recorded separately with safe error metadata.
- Never replace a valid snapshot with fabricated or simulated data.

If a result has candidates plus unavailable items, classify it as PARTIAL_SUCCESS.

If an empty result is valid and honestly counted, classify it as EMPTY_SUCCESS.

==================================================
8. MEMORY + POSTGRES BEHAVIOR
==================================================

Use PostgreSQL as the durable source of truth and memory as a fast cache.

Startup sequence:

1. start application normally
2. load latest valid snapshot from PostgreSQL
3. place it in the in-memory snapshot cache
4. serve /api/opportunities/latest immediately when one exists
5. start a new background scan asynchronously
6. replace memory and PostgreSQL latest state only after a new valid result is persisted

Do not delay server startup waiting for MCP.

If PostgreSQL loading fails:

- log safely
- continue running
- background scan may still attempt later
- dashboard shows honest unavailable/initializing state

If MCP refresh fails:

- keep serving the previous valid snapshot
- attach stale/failure metadata where the current contract supports it
- do not set the snapshot to null

==================================================
11. OVERLAP PROTECTION
==================================================

Ensure a second scan cannot start while one is already running.

At minimum preserve an in-process running guard.

For multi-instance safety, inspect whether PostgreSQL advisory locks are already used.

Preferred:

Use a PostgreSQL advisory lock around the background scan.

Requirements:

- only one Railway instance performs a scan
- another instance skips safely
- lock releases after success or failure
- deployment/restart does not permanently orphan the lock
- no second scan begins during an active scan

If advisory locking cannot be implemented safely with current database conventions, report that honestly and implement the strongest compatible protection, but do not silently assume a permanent single instance.

==================================================
12. FAILURE AND STALE-WHILE-REFRESH
==================================================

Behavior:

Fresh valid snapshot
→ serve normally

Background refresh running
→ serve previous valid snapshot with refreshStatus = running

Refresh failed
→ serve previous valid snapshot with refreshStatus = failed and safe warning

Snapshot older than the configured freshness policy
→ serve it with freshnessStatus = stale

No valid snapshot
→ return snapshot: null

Do not hide a valid previous snapshot because the most recent refresh failed.

==================================================
13. RETENTION
==================================================

Keep valid snapshots for 30 days initially.

Keep failed-attempt records for a shorter period, such as 7 days.

Implement retention using an existing cleanup convention or a bounded cleanup call after successful scans.

Requirements:

- cleanup is non-blocking where practical
- cleanup failure does not fail a successful scan
- no unrelated records are deleted
- retention duration is documented

Do not build a data warehouse.
