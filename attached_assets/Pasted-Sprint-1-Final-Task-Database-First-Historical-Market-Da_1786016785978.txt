Sprint 1 Final Task — Database-First Historical Market Data for Deterministic Scanning

PRIMARY REPOSITORY

Implement this in the existing VCP Trader AI / StrategyAgent repository using Replit.

PROJECT CONTEXT

VCP Trader AI currently has:

- a background Opportunity Engine
- PostgreSQL opportunity snapshot persistence
- a dashboard that reads stored opportunity snapshots
- an MCP service that performs deterministic scanning and ranking
- Twelve Data market-data integration
- supported broker integrations, including Tradier and TradeStation
- future support planned for Schwab and other established brokers
- MCP session recovery
- market-history concurrency limits
- retry and timeout protection
- safe failure handling
- no simulated opportunity fallback in production

Production investigation confirmed that the internal MCP-facing history route currently uses Twelve Data as its sole provider and that repeated scan-time requests can encounter quota, wait, timeout, malformed-response, and provider errors. :contentReference[oaicite:0]{index=0}

The investigation also confirmed that the current credit gate may wait or fail before the provider request and that provider failures are currently surfaced through the internal history endpoint. :contentReference[oaicite:1]{index=1}

PRODUCT GOAL

Build a reliable and monetizable platform that helps self-directed traders and investors:

- discover opportunities
- understand why they qualify
- evaluate risk
- monitor changing conditions
- prepare and submit self-directed orders through supported brokers

This task must improve the reliability and scalability of the existing product without changing its product direction.

ARCHITECTURAL GOAL

Historical technical analysis and broad deterministic market scanning should primarily use validated market history stored in VCP Trader PostgreSQL.

External providers should populate or refresh that stored history.

The Opportunity Engine should not repeatedly request full historical datasets from Twelve Data during every market-wide scan when sufficiently fresh stored bars already exist.

APPROVED EXTERNAL MARKET-DATA SOURCES

Production market data may come only from:

1. Twelve Data
2. An established supported broker connection
3. Future established broker integrations added through the approved broker-provider interface

Examples include:

- Tradier
- TradeStation
- Charles Schwab
- Interactive Brokers
- other future supported and properly integrated brokers

Do not hardcode the architecture around Tradier alone.

Disallowed production sources:

- Yahoo Finance
- mock providers
- hash-generated prices
- synthetic OHLCV
- undocumented fallback providers
- fabricated options chains
- simulated values presented as current data

Do not commit, push, migrate, or deploy automatically.

3. DEFINE MARKET-DATA RESPONSIBILITIES
==================================================

Implement and document this responsibility model.

A. PostgreSQL historical-bar store

Primary source for:

- historical OHLCV used by deterministic scanning
- moving averages
- RSI
- ATR
- trend classification
- VCP structure
- breakout structure
- pullback structure
- volume analysis
- market-regime history

B. Twelve Data

Approved external source for:

- scheduled historical-bar ingestion
- missing-history backfill
- bar refresh when stored history is absent or stale
- broker-independent quotes and market data supported by the subscription
- current or delayed data when accurately labeled

C. Established broker connections

Broker-provider interface may supply:

- current quote
- bid and ask
- extended-hours quote
- live or entitled intraday data
- options chains
- Greeks
- open interest and volume
- account positions
- buying power
- order status
- execution

A supported broker may also supply historical bars when:

- the broker integration explicitly supports them
- entitlement is valid
- the data passes the same canonical validation
- the source is recorded
- using broker history does not make global deterministic scan results user-dependent

D. Deterministic global scanning

Global Opportunity Engine scans should use a consistent, user-independent historical dataset.

Recommended source:

PostgreSQL bars populated primarily through Twelve Data ingestion.

Do not make global rankings differ based on which broker an individual user connected.

E. User-specific live context

A user-facing analysis may supplement the stored historical analysis with a current quote from any established connected broker.

The source must be accurately labeled.

==================================================

Suggested responsibility:

getHistoricalBars({

The service should:

3. read stored PostgreSQL bars

Do not let individual callers independently implement provider selection.

==================================================
7. PROVIDER PRECEDENCE
==================================================

Use purpose-aware precedence.

A. Global deterministic scanner history

1. sufficiently fresh validated PostgreSQL bars
2. Twelve Data backfill/refresh
3. an approved non-user-specific broker-market-data feed only if explicitly configured for global use
4. unavailable

Do not use a user’s private broker connection for a global market scan.

B. User-requested symbol history

1. sufficiently fresh validated PostgreSQL bars
2. established connected broker history when supported and entitled
3. Twelve Data backfill/refresh
4. unavailable

C. User-requested current quote

1. established connected broker quote when supported and valid
2. Twelve Data
3. unavailable

D. Options chain

1. established connected broker options feed
2. another explicitly approved real options provider in the future
3. unavailable or clearly labeled estimated strategy concept

Do not fabricate current options contracts.

==================================================
8. STORED-BAR FRESHNESS POLICY
==================================================

Define freshness based on interval and market session.

For daily bars:

- latest completed trading-day bar is fresh
- current incomplete daily candle must not replace a completed daily bar unless explicitly supported
- weekends and market holidays must not incorrectly mark Friday’s bar stale
- use an existing market calendar if available
- otherwise implement a conservative documented policy

For intraday bars:

- define interval-specific freshness
- do not claim real-time freshness when data is delayed
- preserve provider timestamps

For long-term analysis:

- historical bars can remain reusable while current quote context is refreshed separately

Do not use only wall-clock age without considering market sessions.

==================================================
9. HISTORY DEPTH REQUIREMENTS
==================================================

Define minimum history requirements by analysis purpose.

Examples to verify against actual algorithms:

- moving averages: enough bars for the longest required period plus warm-up
- VCP analysis: enough trading days for base and contraction detection
- ATR: required lookback plus warm-up
- market regime: sufficient index history
- ranking: enough data for every required metric

Do not invent a single outputSize for all tools.

Create explicit policy constants or configuration based on actual algorithm needs.

If insufficient history exists:

- mark the analysis unavailable or partial
- request an approved backfill when allowed
- do not calculate misleading indicators from undersized data

10. INGESTION AND BACKFILL
==================================================

Reuse the existing ingestion scheduler where possible.

Required capabilities:

- scheduled daily-bar refresh
- bounded symbol batches
- approved concurrency
- credit-aware requests
- in-flight deduplication
- retries for transient provider failures
- idempotent upsert
- no duplicate bars
- incremental refresh
- missing-history backfill

Recommended behavior:

- existing symbol with current history → request only missing bars or a small overlap window
- new symbol → bounded historical backfill
- corporate-action or correction case → controlled revalidation window
- failed symbol → record failure without aborting the entire ingestion batch

==================================================
12. INTERNAL MCP HISTORY ROUTE
==================================================

Preserve the existing authenticated internal route where possible:

GET /api/internal/market/history

Change its behavior from an external-provider proxy into a canonical history-service endpoint.

Preferred route behavior:

1. authenticate internal request
2. validate symbol/interval/outputSize
3. call canonical historical-bar service
4. return stored validated bars immediately when sufficient
5. optionally perform an approved refresh when required
6. include source and freshness metadata
7. return an honest error when unavailable

The MCP contract should remain compatible unless additive metadata is introduced.

Do not force MCP to know whether bars came from PostgreSQL, Twelve Data, Tradier, TradeStation, Schwab, or another approved broker.

That provider abstraction belongs in VCP Trader.

==================================================
13. PREVENT SCAN-TIME EXTERNAL REQUEST STORMS
==================================================

For Opportunity Engine and broad MCP scans:

- stored PostgreSQL bars should satisfy the normal scan path
- external refreshes should not occur independently for dozens of symbols during the same ranking request
- if data is missing, queue backfill separately or use a bounded controlled refresh stage
- one scan must not trigger dozens of uncontrolled external API requests
- return unavailable counts honestly for symbols not yet backfilled

Preferred sequence:

scheduled ingestion/backfill
→ validated PostgreSQL bars
→ MCP deterministic scan
→ stored opportunity snapshot
→ dashboard

Do not let dashboard access trigger external history ingestion.

==================================================

Validate all bars before storage or use:

- positive prices
- non-negative volume
- high >= open/close/low

==================================================
19. FAILURE BEHAVIOR
==================================================

Expected behavior:

Stored bars sufficient
→ return immediately

Stored bars stale/missing and approved refresh succeeds
→ validate, persist, return

Refresh fails but stored bars remain usable under policy
→ return stored bars with stale/limited metadata

Refresh fails and stored bars are unusable
→ unavailable

One symbol fails
→ other symbols continue

Market-data readiness too low
→ preserve previous opportunity snapshot
→ record a safe failed or partial scan attempt

Never return:

- Yahoo data
- mock data
- fabricated bars
- silent provider substitution
- an empty array presented as successful complete history
