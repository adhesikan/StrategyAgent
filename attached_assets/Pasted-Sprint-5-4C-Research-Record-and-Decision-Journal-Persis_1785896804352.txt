Sprint 5.4C — Research Record and Decision Journal Persistence Foundation

CURRENT STATE

The vcp-trader-mcp repository now contains deterministic pure research-evidence extractors for:

- SYMBOL_ANALYSIS
- TRADE_RESEARCH
- MARKET_OPPORTUNITY_SEARCH
- PORTFOLIO_GOAL_RESEARCH
- PORTFOLIO_IMPACT
- OPTIONS_RESEARCH

The approved architecture uses Option A:

MCP result
→ validated by StrategyAgent
→ matching pure research-evidence extractor
→ immutable ResearchEvidenceRecord
→ VCP Trader persistence layer

No new MCP tool was added.

GOAL

Create a secure, user-owned persistence foundation for immutable deterministic ResearchEvidenceRecords and user-authored Decision Journal entries.

This is a research and decision-support feature.

Do not:

- modify MCP algorithms
- modify scanner, ranking, recommendation, portfolio, options, or risk logic
- add autonomous recommendations
- add automatic execution
- store private chain-of-thought
- store account IDs, broker identifiers, credentials, context tokens, or raw portfolio payloads
- commit, push, or deploy automatically

==================================================
4. OWNERSHIP AND AUTHORIZATION
==================================================

Enforce server-side ownership for every operation.

Required protections:

- create record only for authenticated user
- list records only for authenticated user
- fetch by id only when owned
- update metadata only when owned
- archive only when owned
- delete only when owned
- journal record must belong to the same user as its research record
- no cross-user parentRecordId
- no cross-user conversation linking
- no client-supplied userId accepted

Return 404 rather than revealing existence of another user’s record when consistent with existing conventions.

==================================================
5. RESEARCH EVIDENCE VALIDATION
==================================================

Port or safely mirror the ResearchEvidenceRecord runtime schema into StrategyAgent.

Preferred approach:

- use a shared package only if the repositories already support one cleanly
- otherwise create a strict local schema matching schemaVersion 1.0
- document synchronization ownership

Validate every record before persistence.

Reject:

- unknown schema version
- unknown domain
- mismatched domainSnapshot
- malformed dates
- non-finite numbers
- unknown top-level or nested fields
- oversized arrays/strings
- forbidden sensitive keys

Do not persist partially valid evidence.

==================================================
6. SAFE-FIELD DEFENSE IN DEPTH
==================================================

Before persistence, scan the final serialized record for forbidden fields or values:

- accountId
- accountNumber
- brokerAccount
- brokerId
- connectionId
- userId inside evidence payload
- accessToken
- refreshToken
- serviceToken
- apiKey
- authorization
- optionsContextToken
- portfolioContextToken
- rawPositions
- rawPortfolio
- providerPayload
- stack
- systemPrompt
- developerPrompt
- chainOfThought

The outer database userId is allowed.

The evidence JSON itself must never contain these fields.

On violation:

- reject persistence
- emit a safe structured error
- do not log the offending value

8. API ENDPOINTS
==================================================

Add authenticated endpoints such as:

POST /api/research-records
GET /api/research-records
GET /api/research-records/:id
PATCH /api/research-records/:id/metadata
POST /api/research-records/:id/archive
DELETE /api/research-records/:id

POST /api/research-records/:id/journal
GET /api/research-records/:id/journal
PATCH /api/research-records/:id/journal
DELETE /api/research-records/:id/journal

For POST /api/research-records:

Prefer creation from trusted server-held evidence generated during the current request.

Do not allow the browser to submit an arbitrary ResearchEvidenceRecord and claim it came from MCP unless the architecture already includes a signed or server-cached evidence reference.

Preferred safe pattern:

1. TraderBrain creates validated evidence server-side.
2. Server stores it temporarily under a short-lived evidence ID.
3. Frontend sends only the evidence ID when the user clicks Save Research.
4. Server resolves evidence ID, verifies user/session binding and expiry, then persists it.

Alternative:

Persist automatically after explicit server-side save intent.

Do not accept arbitrary client-authored deterministic evidence.

==================================================
9. SHORT-LIVED SAVE HANDLE
==================================================

Implement a short-lived server-controlled save handle:

ResearchSaveHandle {
  id;
  userId;
  requestId;
  evidence;
  expiresAt;
  consumed;
}

Requirements:

- opaque random ID
- bound to authenticated user/session
- short TTL, recommended 10 minutes
- single-use or safely idempotent
- never exposed to OpenAI
- contains no credentials
- not stored in browser localStorage
- expired handles rejected
- cross-user use rejected

Use existing cache/storage infrastructure where practical.

If an existing trusted-context token mechanism is reusable, use the same principles but do not mix scopes.

==================================================
10. INTEGRATE WITH TRADERBRAIN OUTPUT
==================================================

After TraderBrain produces deterministic evidence for supported domains:

- invoke the matching research-evidence extractor
- validate the evidence
- mint a researchSaveHandle
- return only safe metadata to the frontend:

researchSave?: {
  available: true;
  handleId;
  domain;
  titleSuggestion;
  expiresAt;
}

Do not automatically persist on every Ask AI response.

The user must explicitly choose Save Research.

Do not create save handles for:

- education-only responses
- failed requests with no deterministic evidence
- generic conversation
- malformed or unsafe evidence
- pure OpenAI prose
