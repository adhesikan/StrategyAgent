TASK #175 — Secure Institutional API Access with Keys and Usage Controls

This task is the blocking parent for Task #178.

Objective:
Complete the external /api/v1 authentication, authorization, API-key,
rate-limiting, and usage-control layer so external applications can securely
consume the Institutional Intelligence API.

IMPORTANT:
Work ONLY on Task #175.

Do not start Task #178.
Do not build the external demo.
Do not add new analytics.
Do not modify Institutional Intelligence UI unless absolutely required for
API compatibility.
Do not fix unrelated repository-wide TypeScript errors.

First inspect the existing API/security implementation because some or all of
this infrastructure may already exist.

Reuse existing authentication, database, middleware, logging, and rate-limit
patterns where appropriate.

--------------------------------------------------
1. EXTERNAL API AUTHENTICATION
--------------------------------------------------

Protect external /api/v1 institutional endpoints using API keys.

Expected request:

Authorization: Bearer <api-key>

Support recognizable key prefixes:

sm_live_
sm_test_

Do NOT store complete plaintext API keys in the database.

At creation:
- generate cryptographically secure key
- display/return complete key once
- persist secure hash
- persist non-secret prefix/identifier sufficient for lookup
- never make the raw key retrievable afterward

Never log complete API keys.

--------------------------------------------------
2. API CLIENT / KEY DATA MODEL
--------------------------------------------------

Inspect existing schema first and reuse anything already implemented.

Provide the equivalent of:

api_clients

- id
- name
- owner/user reference where appropriate
- status
- createdAt
- updatedAt

api_keys

- id
- clientId
- name
- keyPrefix
- keyHash
- environment/test-vs-live
- createdAt
- lastUsedAt
- expiresAt optional
- revokedAt optional
- status

Follow existing naming/database conventions.

Create migrations only if required.

--------------------------------------------------
3. SCOPES
--------------------------------------------------

Support API scopes.

Planned scopes:

institutional:read
multibagger:read
fundamentals:read
research:read

For Task #175, institutional:read must be fully functional.

If Multibagger public v1 endpoints already exist and are intended for external
consumption, support multibagger:read as well.

Do not implement unrelated fundamentals/research APIs merely to satisfy the
scope enum.

Authorization rules must distinguish:

401 = missing/invalid authentication

403 = valid key but insufficient permission/scope

--------------------------------------------------
4. PROTECT /api/v1
--------------------------------------------------

Identify which /api/v1 routes are intended to be externally accessible.

At minimum protect the institutional intelligence endpoints, including:

/api/v1/institutional/funds/...
/api/v1/institutional/stocks/...
/api/v1/institutional/trends/...
/api/v1/institutional/rotation/...

Protect Multibagger v1 endpoints with multibagger:read if those routes are
already part of the external API.

Do NOT accidentally change existing application-session authentication under:

/api/institutional/...

The existing StockMetrics application must continue working.

Health endpoints may remain unauthenticated if that matches the existing API
design.

--------------------------------------------------
5. RATE LIMITING
--------------------------------------------------

Implement API-key/client-based rate limiting.

Do not hardcode rate-limit policy throughout route files.

Make limits configurable by client/tier or centralized configuration.

Rate limiting should operate on authenticated API identity where possible,
rather than treating all external users as one IP.

Return HTTP 429 when exceeded.

Return useful rate-limit metadata/headers where consistent with existing
architecture.

Do not leak sensitive client information.

--------------------------------------------------
6. USAGE METERING
--------------------------------------------------

Track external API usage.

Capture at minimum:

apiClientId
apiKeyId or safe key identifier
endpoint/route
HTTP method
response status
request timestamp
response time/duration

Optionally capture request ID and safe usage dimensions already available.

Do NOT store:

raw API key
Authorization header
sensitive secrets

Usage recording should not expose internal stack traces to clients.

Design this so we can later support:

usage dashboards
API plans
quotas
billing
partner licensing

without implementing billing now.

--------------------------------------------------
7. KEY MANAGEMENT
--------------------------------------------------

Implement server/domain capabilities for:

create API key
list key metadata
revoke API key

Never return existing raw keys from list operations.

If key rotation fits naturally into the architecture, structure the service so
rotation can be added later, but do not overbuild it.

Use existing application authorization rules to ensure ordinary users cannot
manage other clients' API keys.

--------------------------------------------------
8. SECURITY
--------------------------------------------------

Verify:

- cryptographically secure key generation
- secure hashing
- constant-time comparison where applicable
- raw keys not persisted
- raw keys not logged
- Authorization headers not logged
- revoked keys fail
- expired keys fail
- disabled clients fail
- incorrect scopes fail
- malformed bearer headers fail safely
- API errors do not reveal hashes/database internals
- SQL remains parameterized

Do not invent custom cryptography if the repository already contains an
appropriate secure library/pattern.

--------------------------------------------------
9. RESPONSE / ERROR CONTRACT
--------------------------------------------------

Preserve the existing /api/v1 response architecture.

Authentication/authorization errors should follow the standard API error
envelope where applicable:

{
  "error": {
    "code": "...",
    "message": "...",
    "requestId": "..."
  }
}

Use stable machine-readable codes such as equivalents of:

API_KEY_REQUIRED
API_KEY_INVALID
API_KEY_EXPIRED
API_KEY_REVOKED
API_CLIENT_DISABLED
INSUFFICIENT_SCOPE
RATE_LIMIT_EXCEEDED

Use the project's existing conventions if these already exist.
