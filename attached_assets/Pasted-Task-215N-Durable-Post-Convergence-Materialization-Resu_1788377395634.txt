OBJECTIVE

Make post-convergence downstream materialization durable and resumable across
process failure, deploy, restart, or operator retry.

The system must be able to recover after:

1. duplicate convergence database mutation commits
2. downstream materialization partially or fully fails
3. process exits
4. a later invocation resumes exactly the required downstream rebuild
   without needing duplicate groups to still exist

DESIGN REQUIREMENTS

Introduce a durable convergence journal/checkpoint using existing production
database infrastructure.

Persist enough information BEFORE or DURING the mutation transaction to
reconstruct the downstream rebuild scope after commit.

The durable record should include at minimum:

- convergence run id
- plan hash
- status
- created/updated timestamps
- affected canonical accessions
- affected periods
- exact affected symbols
- exact downstream targets where already supported
- mutation completion status
- materialization completion status
- last completed materialization stage
- failure stage
- sanitized failure reason
- retry count or attempt metadata

Use normalized/bounded storage appropriate for the current schema.
Do not persist secrets or raw SEC payloads.

CRITICAL INVARIANT

Once mutation commits, the rebuild scope must remain durably available even
if the process crashes immediately afterward.

A rerun must discover the unfinished convergence run from the journal and
resume materialization from persisted scope.

It must NOT regenerate the scope by rescanning for duplicates.

RESUME BEHAVIOR

- detect unfinished convergence run for the same plan/run

- resume only missing downstream materialization stages
- make each downstream stage idempotent
- mark completion only after all required stages succeed

If a retry is safe, resume automatically within the explicit command flow.

If persisted state is inconsistent, fail closed.
