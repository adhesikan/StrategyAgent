# Phase 6: Credit-Limit Manager

Implement a persistent server-side Twelve Data credit manager.

Twelve Data charges API credits by endpoint weight and number of symbols.

For `/time_series`, initially configure:

- 1 credit per symbol per request

Make endpoint weights configurable.

Track:

- Credits used during the current minute
- Credits used during the current day
- Minute reset time
- Daily reset time
- Endpoint
- Endpoint weight
- Symbols requested
- Request status
- Retry count
- Ingestion run
- Environment
- Caller

Use safety thresholds:

- Maximum 7 credits per minute
- Maximum 750 credits per day

This preserves reserve capacity below the 8-per-minute and 800-per-day limits.

Before every request:

1. Calculate required credits.
2. Check minute availability.
3. Check daily availability.
4. Reserve credits.
5. Queue or delay when the minute safety threshold would be exceeded.
6. Stop optional ingestion when the daily safety limit would be exceeded.
7. Allow administrative visibility into the reason for deferral.
8. Account for retry requests separately.
9. Release or reconcile failed reservation state safely.

If the application can run on multiple instances, do not use only in-memory counters.

Use PostgreSQL, Redis, or the project’s existing distributed locking mechanism.

# Phase 10: Daily Scheduled Ingestion

Create a daily scheduled job.

Recommended schedule:

- After 7:00 p.m. America/New_York
- On expected US trading days

Do not assume market data is finalized immediately at 4:00 p.m.

Workflow:

1. Acquire a distributed job lock.
2. Load enabled symbols.
3. Check current credit budget.
4. Determine each symbol’s latest stored date.
5. Request a small recent history window to capture new or corrected bars.
6. Normalize the provider response.
7. Validate all bars.
8. Upsert new or corrected records.
9. Recalculate affected indicators.
10. Generate internal daily analysis snapshots.
11. Run internal Opportunity Radar.
12. Run internal Analysis Conditions.
13. Update Probability Engine daily factors.
14. Preserve the previous valid snapshot until the new snapshot passes validation.
15. Mark the new snapshot current.
16. Record the ingestion result.
17. Release the distributed lock.
18. Notify admins on repeated or material failures.

Handle:

- Weekends
- US market holidays
- Delayed data publication
- Provider outages
- Partial failures
- Duplicate job starts
- Corrected historical bars
